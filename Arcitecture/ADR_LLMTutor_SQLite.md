## Context

LLMチューター（Flask + Vertex AI）では、対話履歴をプロンプトに含めることで文脈を維持する必要がある。現状は `chat_history` が常に空であり、毎回「直前1発言」しかLLMに渡っていない。

そこで、以下の要件を満たすデータストアを選定する必要がある。

- セッションIDで紐づけた対話（user/assistant）の永続化ができること
- 同一セッション内のメッセージを時系列で取得し、直近N件をプロンプトの `history` に組み込めること
- LLMチューター単体で動作すること（LAD・視聴ログ・小テスト等の外部データ連携は本決定の対象外）
- 開発者が一人であり、運用コストを抑えたいこと
- まずは「数人〜十数人規模」で確実に動くことを目標とし、スケールはその後に考えること

## Decision

**対話履歴の保存先として、SQLite を採用する。**

### 1. データストアの役割

- **対話履歴**: セッション（sessions）とメッセージ（messages）を SQLite に格納する。セッションIDをキーに、送受信のたびに永続化し、プロンプト組み立て時に直近Nターンを取得して `history` に渡す。
- **その他**: 視聴ログ・小テスト・LAD は本ADRの対象外（現状どおり Spreadsheet 等は別途）。

### 2. 比較検討

データストア選定において、以下のように比較を行った。

| 比較項 | SQLite | PostgreSQL / MySQL（Docker等） | クラウドDB（Firestore / Cosmos DB 等） | ファイル（JSON/CSV） |
|--------|--------|--------------------------------|----------------------------------------|----------------------|
| 導入コスト | ✅ ゼロ（標準ライブラリで利用可能） | 🔺 コンテナ・サーバの用意が必要 | ❌ アカウント・課金・ネット依存 | ✅ 低い |
| 開発環境 | ✅ 1ファイルで完結、再現が容易 | 🔺 Docker 等の起動が必要 | 🔺 エミュレータ or 本番依存 | ✅ 単純 |
| 検索・時系列取得 | ✅ SQLで session_id + created_at の範囲取得が容易 | ✅ 同様に可能 | ✅ 可能（クエリ設計による） | ❌ 自前で読み込み・ソートが必要 |
| スキーマ・整合性 | ✅ スキーマ固定で履歴の構造を保証できる | ✅ 同様 | 🔺 NoSQL は柔軟だが今回の要件では過剰 | ❌ 形式の揺れ・破損のリスク |
| 同時アクセス | ✅ 数人〜十数人規模なら十分 | ✅ 高負荷にも強い | ✅ スケールしやすい | ❌ ファイルロック・競合の考慮が必要 |
| 運用・デプロイ | ✅ ファイル1つでバックアップ・移行が容易 | 🔺 コンテナ/DBのライフサイクル管理 | 🔺 ネット・課金・リージョン | ✅ ファイルの扱いのみ |
| スケール | 🔺 単一ファイル・単一Writerの制約あり | ✅ スケールの余地が大きい | ✅ クラウドのスケール | ❌ 大容量で非現実的 |

以上により、「数人〜十数人規模」「LLMチューター単体」「開発者一人・運用コスト最小」という前提では、**追加インフラなしでスキーマを保った履歴の永続化ができ、開発・デプロイが最も簡単な SQLite が最適**であると判断した。スキーマは固定（sessions / messages）でよく、NoSQL の柔軟性は不要である。将来、同時接続やデータ量が増えた場合は、同一スキーマで PostgreSQL 等へ移行する選択肢を残す。

### 3. 採用する構成

- **DB**: SQLite 1ファイル（例: `data/tutor.db`）。パスは環境変数で上書き可能とする。
- **アクセス**: Python では `sqlite3` 標準ライブラリ、または軽量な ORM（例: SQLAlchemy）で sessions / messages の CRUD を実装する。
- **スキーマ**: 別途「対話履歴DB設計」で定義した `sessions`（id, created_at）と `messages`（id, session_id, role, content, created_at）を用いる。

## Consequences

この決定により生じるメリットと、受け入れるべき負債・リスクは以下の通りである。

### メリット

- **導入の簡素さ**: 追加サーバ・クラウド契約なしで、対話履歴の永続化をすぐに開始できる。
- **開発・検証のしやすさ**: 1ファイルで完結するため、ローカル・CI での再現が容易で、バックアップや移行もファイルコピーで対応できる。
- **DESIGN.md との整合**: 「対話履歴用 DB（例: SQLite）。セッションID・role・content・created_at 等のスキーマ」という方針（3.2 データ基盤）を満たす。

### 受け入れるべき負債・リスク

- **スケールの上限**: 同時書き込みが増えると SQLite の制約（単一Writer 等）に当たる可能性がある。対象規模（数人〜十数人）を超える前に、PostgreSQL 等への移行を検討する。
- **バックアップの責任**: DB ファイルの破損や消失を防ぐため、バックアップ手順を運用で定める必要がある（例: 定期コピーやデプロイ時の取り扱い）。
- **本番の配置**: 同一サーバ上でファイルとして配置する前提のため、マルチインスタンスで同一ファイルを共有する構成は取れない。現時点の単一インスタンス運用では許容する。

## Compliance

この決定を実装・運用する上で、守るべきルールは以下の通りとする。

### データ・DB設計

- **格納対象**: SQLite には対話履歴（sessions, messages）のみを格納する。視聴ログ・小テスト結果等は本DBには保存しない。
- **スキーマ変更**: テーブル定義の変更は、マイグレーションスクリプトまたは schema.sql で明示し、バージョン管理する。
- **パス管理**: DB ファイルパスは環境変数（例: `TUTOR_DB_PATH`）で指定可能とし、デフォルトはプロジェクト内の `db/data/tutor.db` とする。

### 実装

- **履歴の取得**: プロンプト組み立て時は、必ず `session_id` を指定し、`created_at` 昇順で直近 N 件（またはトークン上限に合わせた件数）を取得して `history` に渡すこと。
- **永続化のタイミング**: ユーザー発言受信後と LLM 応答取得後に、それぞれ 1 件ずつ `messages` に INSERT すること。
