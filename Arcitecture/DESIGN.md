# 学習振り返り支援システム 設計まとめ

学習分析ダッシュボード（LAD）と LLM チューターを用いた学習振り返り支援システムの改良設計をまとめたドキュメントである。

---

## 1. システム概要と現状

### 1.1 構成

| コンポーネント | 技術 | 役割 |
|----------------|------|------|
| 学習分析ダッシュボード（LAD） | Looker Studio | 学習データの可視化（実験者・学習者向け） |
| 動画視聴プラットフォーム | Google Apps Script（GAS）＋HTML | YouTube 埋め込み・視聴ログ記録 |
| 小テスト | Google Form | 回答収集 |
| LLM チューター | Flask（app.py）＋Vertex AI（Gemini） | 自己調整学習（SRL）の振り返り対話支援 |

### 1.2 現状のデータフロー

- **学習環境**: 学習者が GAS の動画で視聴、Form で小テスト。データは **Google Spreadsheet** に自動追記される。
- **振り返り環境**: app.py はリクエストのたびに Spreadsheet を読み、視聴ログ・小テスト結果をプロンプトに載せて LLM に渡す。LAD は Looker Studio が Spreadsheet を参照するが、**実験者の手動アップロード**を経ないと Looker に反映されない。
- **会話**: app.py の `chat_history` は常に空。LLM には毎回「直前 1 発言」しか渡っていない（文脈なし）。
- **教材コンテキスト**: 動画字幕の RAG は未実装（コメントアウト済み）。

### 1.3 主な課題

| 課題 | 内容 |
|------|------|
| リアルタイム連携の欠如 | 手動アップロードが「ダム」となり、LAD の反映が遅れる。実験者が増えると運用が破綻する。 |
| LLM の短期記憶の欠如 | 対話履歴をプロンプトに含めていないため、文脈のない回答になる。 |
| 字幕の未活用 | 動画のどこが難しかったかの対話に、字幕データが使われていない。 |
| Web vs ローカル | 現状は Web。ローカルアプリ化は「使い勝手・開発のしやすさ」の議論であり、構造的欠陥の修正より後回しとする。 |

---

## 2. 目標・価値・制約

### 2.1 価値の一文

**誰が**: 数人〜十数人規模の自学習者が  
**何をした結果**: 学習直後に自動更新される LAD と、最新ログを即座に反映しつつ過去の対話も覚えている LLM チューターを利用することで  
**どうなる**: 実験者の介入を待たず、学習の熱が冷めないうちに「今この瞬間」の課題に対する自己調整学習を**完遂しやすくできる**。

※ まずは「数人〜十数人で確実に動く」ことを目標とし、スケールはその後に考える。

### 2.2 LAD の役割

- **学習者向け**: メタ認知的モニタリングの支援（自分の視聴ログ・小テスト結果を「今」把握できる）。
- **実験者向け**: 集計・分析は別途方針を整理（手動アップロードの削減や別ツールの検討）。

### 2.3 制約

**技術・運用**

- **スケーラビリティ**: 実験者が「LAD 更新依頼」や手動 CSV アップロードをする工程をゼロにする。
- **フィードバックの即時性**: 自己省察は学習直後が効果的であるため、データの反映ラグを許容しない。実装では「○秒以内」など許容ラグを数値で定義する。
- **LAD 更新のコスト**: 「データ更新がありました」とアラートを出し、**学習者がロードしたタイミングで LAD を再取得する**形でコストを抑える（プッシュ型のリアルタイム同期は必須としない）。

**スキル・リソース**

- 開発者は一人。app.py（Flask）と Looker Studio の組み合わせを維持する場合、Looker のデータ更新頻度制限（例: 15 分〜）の回避が必要。その一案として、学習者向け表示を app.py 側に Chart.js 等で持つことも検討する。

## 3. 改良後の方針（データ・コンポーネント）

### 3.1 データの流れ（方針）

- **視聴ログ・小テスト**: 当面は Spreadsheet に蓄積する現状を維持。app.py は「最後にログが更新された時刻」を返す API を用意し、フロントはロード時または一定間隔でその時刻を比較。「更新あり」ならアラート表示し、表示用データを再取得する。
- **対話履歴**: **DB に格納**する。セッション ID を発行し、送受信のたびに永続化。LLM には直近 N ターン（またはトークン上限に合わせて）をプロンプトに含める。古い部分は要約する方針を検討する。
- **字幕**: 取得・整形して DB またはファイルに保存し、対話クエリに応じて RAG（または固定コンテキスト）でプロンプトに含める。

### 3.2 コンポーネントと役割

| ブロック | 内容 |
|----------|------|
| **データ基盤** | 対話履歴用 DB（例: SQLite）。セッション ID・role・content・created_at 等のスキーマ。字幕ストア。 |
| **連携・即時性** | 「最終更新時刻」API、フロントのロード時／間隔での比較、アラート＋再取得。手動アップロードの排除。 |
| **会話・文脈** | 履歴の永続化、プロンプトへの履歴組み込み（件数・トークン・要約方針）。 |
| **RAG・コンテキスト** | 字幕の取得・整形・ストア、検索とプロンプトへの付与。 |
| **クライアント** | 現状は Web（Flask＋フロント）。ローカルアプリ／SPA 化は余裕ができたら検討。 |

### 3.3 依存関係

- 会話履歴を渡すには「セッション ID と履歴の保存先」が必要 → データ基盤（履歴用 DB）を先に決める。
- 字幕を RAG に含めるには「字幕の取得とストア」が必要 → データ基盤の一部。
- 優先順位は **履歴（設計→永続化→プロンプト組み込み）を最優先** とし、その次に LAD 自動化、その次に字幕 RAG とする。

---

## 4. 優先順位とプロダクトバックログ

### 4.1 優先順位（実験継続を守るため）

1. **最優先**: データ連携の自動化と LLM の短期記憶（履歴）
   - ここが改善されないと、実験対象者を増やした瞬間にシステムが破綻する。
2. **その次**: 字幕データの RAG 統合
   - 対話の質（「動画のどこが難しかったか」への踏み込み）を高める。
3. **余裕ができたら**: Web からローカルアプリ（または SPA）への移行
   - 使い勝手・開発のしやすさの議論。構造的欠陥の修正より後回しでよい。

| Day | 内容 | 主なラベル |

| 2 | 対話履歴の永続化実装 | priority: high, theme: history |
| 3 | プロンプトへの履歴組み込み | priority: high, theme: history |
| 4 | LAD「データ更新あり」アラート＋ロード時更新 | priority: high, theme: lad, data |

| 6 | 視聴ログ・小テストの簡易グラフ実装（Chart.js） | priority: high, theme: lad |
| 7 | 実験者向けデータ参照の整理 | priority: medium, theme: data |
