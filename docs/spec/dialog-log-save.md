# 対話ログの保存 — 「対話ログを送信して終了する」とブラウザを閉じるときの確認で、対話ログを確実にDBへ残す

- 状態: **承認済み(PO承認 2026-09-29)**。承認の範囲は、PBI-A-1(13件)・PBI-A-2(6件)・PBI-B(7件)の全 AC と、共有IF の設計案(`POST /api/dialog-log`、`dialog_logs`、JSON のキー、`end_method` の2値、A-1 で2値とも受け付ける変更を含む)。質問 Q1〜Q12、論点 N1〜N10、feasibility の指摘 F1・F4・F7 は PO が決定した(2026-09-29。「POの決定」の節)。
- 本仕様は3つの PBI を含む(PO の決定により分割。同一スプリントで、**A-1 → A-2 → B の順**に進める)。
  - **PBI-A-1**(サーバー側): AI の応答の生成を終えた時刻の記録、変更前の DB への対応、対話ログの保存の受け口(保存 API)と共有IF(「PBI-A-1」の節)。
  - **PBI-A-2**(画面): 「対話ログを送信して終了する」ボタン、完了画面、失敗の表示、再訪(「PBI-A-2」の節)。PBI-A-1 の保存 API を使う。**PBI-A-1 の後**に着手する。
  - **PBI-B**: ブラウザを閉じるときの確認と、離脱時の保存(「PBI-B」の節)。PBI-A-1 の保存 API と PBI-A-2 の画面を使うため、**PBI-A-2 の後**に着手する。
  - 保存が再デプロイ等で失われない基盤(旧案の PBI-C)は、本仕様に含めない(スコープ外・別 Issue)。

## Issue

#11(対話ログを自動的に保存できるようにする)

## 目的(Why)

LLM チューターとの対話ログは、本研究の分析対象である(プロダクトゴール: 研究協力者を通じて効果を検証できる状態にする)。保存を研究協力者の手作業に頼ると、保存を忘れる可能性がある。一度忘れると、その対話を後から取り戻す手段がなく、研究データとして不可逆に失われる。

研究協力者が振り返りを終えるときの操作(「対話ログを送信して終了する」)で対話ログが保存され(PBI-A-1・A-2)、その操作をせずにブラウザを閉じようとしたときにも引き留め、離脱が確定したときに保存を試みる(PBI-B)ことで、研究協力者の注意に頼らずに対話ログを残す。

**ブラウザの制約(一般的な仕様。このリポジトリでの実機確認はしていない)**

- ブラウザを閉じる・タブを閉じる・再読み込み・別ページへ移動するときに出せる確認は、ブラウザ標準のダイアログだけである。現在の Chrome・Safari では、**ダイアログの文言をページ側で変えられない**(ブラウザ既定の「このサイトを離れますか?」等になる)。ボタンもブラウザ既定(「離れる」/「キャンセル」等)。〔`(未確認: ブラウザ仕様の一般知識。実機未確認)`〕

- 標準ダイアログの表示中は、そのタブの他の操作はできない(ブラウザが操作をロックする)。〔`(未確認: 同上)`〕
- Safari では、「戻る」「進む」で、前のページが以前の状態のまま復元されることがある(新たな読み込みにならない)。〔`(未確認: 同上。feasibility-11 F9)`〕

### POの意図(確認済み)

〔出典: Issue #11 の本文(PO 記載)〕

1. 保存形式は JSON。AI とユーザーの2つのロールに分け、時系列で保存する。
2. 「対話ログを送信して終了する」を押すと保存される。
3. 押さないままブラウザを閉じようとすると、「対話ログを送信して終了しますか?」のポップアップを表示する。OK → 保存、キャンセル → 画面に戻る。表示中は他の操作をロックする。
4. 保存された対話ログは DB へ送られる。
5. 研究者がいつでもアクセスできるようにする。アクセス方法は別 Issue(本仕様のスコープ外)。

上記 3 のうち、文言と「OK 後の保存」は、ブラウザの制約により、PO の決定(Q8、F4)のとおりに扱う(文言はブラウザ標準、保存は「発言済みで離脱が確定したとき」に試みるが完了は保証しない、操作のロックはブラウザ側のロックで満たすとみなす)。

〔出典: 「POの決定」の節(2026-09-29、Q1〜Q12 と分割、N1〜N10、F1・F4・F7、大きさの基準の解釈)〕 決定の内容は、次の「POの決定」の節に記す。

**未確認のまま(決定の前提にしない)**: 実験の実施環境(Cloud Run / 学内サーバー / ローカル 等)と実験開始日は、PO から回答がない。消えない保存基盤の別 Issue を起票するときに確認する。本仕様の AC は、これらに依存しない。

## 共通: 保存される対話ログ(JSON)の形と保存 API — 共有IF

PBI-A-1 が作り、PBI-A-2(終了ボタンによる保存)と PBI-B(離脱時の保存)が使い、研究者のアクセスの別 Issue が読み出す。以下を、この節で固定する。**PBI-A-2・PBI-B は、この形を変えない**(変える必要が出たら判断依頼にする)。

以下の具体形(表・列名・キー名・値・API)は、spec-designer の設計案(feasibility F6 への対応)で、PO が承認した(2026-09-29)。決定の理由は、各項目の「理由」に書く。

### 意味(PO の決定から固定)

- **対話ログは、1つの対話セッション(= 1参加者 × 1講義)につき、`tutor.db` に最大1件**。複数回保存したときは、最新の内容で上書きされる(Q6)。
- **識別子**(Q3): participant_id、講義ID、学習セッションID、対話セッションID。
- **終了時刻**: その対話ログを保存した時刻(サーバーが保存を受け付けた時刻)(Q1)。
- **終了の方法**: 「終了ボタン」か「離脱時」かを区別する値(Q8)。
- **発言の並び**: その対話セッションで `tutor.db` の `messages` に保存されているすべての発言(再訪で追記された分を含む)を、時系列の順(`messages` の読み出しの順と同じ。受け付けた時刻の昇順、同じなら保存された順)に並べたもの。
- **発言の時刻**: ユーザーの発言はサーバーが受け付けた時刻、AI の応答は応答の生成を終えた時刻(Q4)。この変更の前に保存された AI の応答は、生成を終えた時刻の記録がないため、「記録なし」を表す値とする。どの時刻とも区別でき、受け付けた時刻で代用しない(N3)。
- **含めないもの**(Q9): 画面だけの固定のあいさつ、AI の応答に失敗したときのエラー表示と、そのときのユーザーの発言、LAD の表示データ(視聴ログ・小テスト)。

### 対話ログの JSON(1件の対話ログ)

```json
{
  "format_version": 1,
  "participant_id": "1",
  "lecture_id": "lecture-1",
  "learning_session_id": "<学習セッションID>",
  "tutor_session_id": "<対話セッションID>",
  "ended_at": "2026-09-29T01:05:00+00:00",
  "end_method": "end_button",
  "messages": [
    {
      "role": "user",
      "content": "<本文>",
      "timestamp": "2026-09-29T01:00:00+00:00"
    },
    {
      "role": "assistant",
      "content": "<本文>",
      "timestamp": "2026-09-29T01:00:07+00:00",
      "utterance_type": "FACT_REQUEST",
      "dialogue_move": "ELICIT_REASON",
      "interpretation_state": {
        "task_understanding": { "status": "unknown", "note": "" },
        "answer_rationale": { "status": "unknown", "note": "" },
        "felt_dissonance": { "status": "unknown", "note": "" },
        "domain_connection": { "status": "unknown", "note": "" },
        "process_memory": { "status": "unknown", "note": "" },
        "lad_connection": { "status": "unknown", "note": "" },
        "ai_hypotheses": { "status": "unknown", "note": "" },
        "learner_load": { "status": "unknown", "note": "" }
      }
    }
  ]
}
```

| キー | 値 | 理由 |
|---|---|---|
| `format_version` | 整数 `1` | 研究者のアクセスの別 Issue や、将来の項目の追加のときに、読み手が形を判別できるようにする |
| `participant_id` | 文字列。画面を開いた participant_id(保存 API に送られた値) | `sessions.participant_id` は空文字のため(前提)、要求の値を使う。Q3 |
| `lecture_id` | 文字列。その参加者の学習セッションの講義ID | Q3 |
| `learning_session_id` | 文字列。`learning.db` の学習セッションID | Q3。研究データの結合キー `(learnerId, learningSessionId)` を含めるため |
| `tutor_session_id` | 文字列。`tutor.db` の対話セッションID(`sessions.id`) | Q3。キー名は、他の識別子と見分けられるよう `session_id` ではなく `tutor_session_id` とする |
| `ended_at` | 時刻の文字列(下記「時刻の形式」) | Q1 |
| `end_method` | `"end_button"`(終了ボタン)または `"page_leave"`(離脱時)。この2つ以外の値はない | Q8。英小文字の固定値にし、画面の文言の変更に影響されないようにする |
| `messages` | 配列。発言の並び。発言0件なら空の配列 `[]` | Q6 |
| `messages[].role` | `"user"` または `"assistant"` | Q4 |
| `messages[].content` | 文字列。保存された本文のまま | |
| `messages[].timestamp` | 時刻の文字列、または `null`(「記録なし」。AI の応答だけに起こる) | N3。`null` はどの時刻の文字列とも区別でき、JSON で最も素直な「値がない」の表現のため |
| `messages[].utterance_type` | (`assistant` だけ)文字列(発話の分類の値。`messages.utterance_type` と同じ)、または記録がなければ `null` | Q4。`user` の発言には、このキー自体を置かない(A6「ユーザーの発言には含まれない」を、キーの有無で判定できるようにする) |
| `messages[].dialogue_move` | (`assistant` だけ)文字列(対話手法の値。`messages.dialogue_move` と同じ)、または記録がなければ `null` | 同上 |
| `messages[].interpretation_state` | (`assistant` だけ)オブジェクト(8つの軸それぞれに `status` と `note`。`messages.interpretation_state` の JSON 文字列を解釈したものと同じ内容)、または記録がなければ `null` | 同上。文字列のまま入れると、研究者が JSON の中の JSON をもう一度解釈する必要があるため、オブジェクトで持つ。A6 の「値が一致」は、`messages.interpretation_state` を JSON として解釈したものと等しいこと、で判定する |

- **時刻の形式**: ISO 8601 の文字列で、秒まで、UTC のオフセット付き(例: `2026-09-29T01:00:00+00:00`)。理由: `tutor.db` の既存の時刻と同じ形式にし、比較と結合を容易にするため。秒未満は切り捨てる(既存と同じ)。このため、受け付けから生成終了までが1秒未満の場合、AI の応答の時刻がユーザーの発言の時刻と同じ値になることがある。

### `tutor.db` の表

**`dialog_logs`(新規)**: 対話ログ。1行 = 1件の対話ログ。

| 列 | 型・制約 | 内容 |
|---|---|---|
| `session_id` | 文字列。**主キー**(一意)。`sessions.id` を参照 | 対話セッションID |
| `participant_id` | 文字列。必須 | JSON の `participant_id` と同じ値 |
| `lecture_id` | 文字列。必須 | JSON の `lecture_id` と同じ値 |
| `learning_session_id` | 文字列。必須 | JSON の `learning_session_id` と同じ値 |
| `end_method` | 文字列。必須 | JSON の `end_method` と同じ値 |
| `ended_at` | 文字列。必須 | JSON の `ended_at` と同じ値 |
| `log_json` | 文字列。必須 | 上記「対話ログの JSON」の全体 |

- **一意性と上書き**: `session_id` を主キーにし、保存は「同じ `session_id` の行があれば置き換え、なければ追加」(upsert)とする。理由: A11(1件だけ)と A12(上書き)を、アプリの判定ではなく DB の制約で保証でき、同時に2つの保存要求が届いても行が2つにならないため。
- **識別子などを列にも持つ理由**: 研究者が SQL で絞り込めるようにするため。JSON だけで完結する(`log_json` だけ取り出しても識別子がそろう)ようにするため、JSON にも同じ値を入れる。列と JSON の値は、同じ保存で書かれ、常に一致する。
- 過去の保存の履歴は残さない(上書き。Q6)。

**`messages`(既存)に列を追加**: `responded_at`(文字列。空を許す)。AI の応答の生成を終えた時刻(時刻の形式は上と同じ)。ユーザーの発言の行と、この変更の前に保存された AI の応答の行では空(記録なし。N3)。既存の列(`created_at` を含む)の値と意味は変えない(AI の応答の `created_at` は、これまでどおり受け付けた時刻で、並び順に使う)。

- **変更前の `tutor.db`**: 起動時に、`dialog_logs` がなければ作り、`messages` に `responded_at` がなければ追加する。既存の行と値は変更しない(A15)。

### 保存 API

| 項目 | 内容 |
|---|---|
| 要求 | `POST /api/dialog-log`、本文は JSON(`Content-Type: application/json`) |
| 本文 | `{"participant_id": "<ID>", "end_method": "end_button" \| "page_leave"}` の2つだけ。対話の本文は送らない(サーバーが `tutor.db` の `messages` から作る) |
| 成功 | 状態 200。本文は JSON `{"tutor_session_id": "...", "ended_at": "...", "end_method": "..."}`(保存した対話ログの値) |
| 要求の誤り | `participant_id` がない・空・空白だけ、`end_method` がない・2つの値以外、本文が JSON でない、のいずれかは、状態 400。対話ログは保存・変更されない |
| 保存の失敗 | DB に書けないなど、サーバー側で保存できなかったときは、2xx 以外の状態を返す(本文の形は定めない)。対話ログは変更されない |

- 理由: 本文を識別子と終了の方法だけにするのは、(1) 対話の内容を改ざんされないため、(2) 離脱時の通信の送れる量の上限に影響されないため(feasibility F4)、(3) 再読み込みで画面が `session_id` を失っても、participant_id から同じ対話セッションに行き着くため(前提)。
- 対話セッション・学習セッションがなければ、保存の時点で作る(N2)。
- `end_method` は、A-1 の時点で2つの値とも受け付ける。A-2 の画面は `end_button` だけを送り、PBI-B の画面は `page_leave` を送る(PBI-B でサーバー側を変えないため)。

## PBI-A-1: 対話ログの保存(サーバー側)

### 実現内容(What)

- AI の応答について、応答の生成を終えた時刻が、新たに `tutor.db` に記録される(Q4)。1往復ごとの保存は、これまでどおり続く(Q1)。
- 保存 API で、その参加者の対話ログが、共有IF のとおりに `tutor.db` の `dialog_logs` に保存される。同じ対話セッションで再び保存したときは、最新の内容で上書きされる(Q6)。
- 発言が0件のときに保存しても、発言の並びが空の対話ログが保存される(Q6)。このとき、まだ学習セッション・対話セッションがなければ、保存の時点で作り、4つの識別子をそろえて保存する(N2)。
- 保存できなかったときは、失敗を示す応答を返す(Q7 の画面の表示の前提)。
- 変更前の形の `tutor.db` でも動く。

### 受入基準(承認済み。PO承認 2026-09-29)

前提(すべての AC に共通): サーバー側の処理(保存 API とその背後の保存処理)で確認する。「保存要求」は、共有IF の保存 API への要求を指す。

1. **A2 保存要求で保存される**: ある参加者がユーザーの発言を2回送り、AI の応答を2回受け取った後に、`end_method` を `end_button` として保存要求を送ると、`tutor.db` に、その対話セッションの対話ログが1件保存され、その `messages` には4件の発言が、`user`・`assistant`・`user`・`assistant` の順で、それぞれ送受信した本文のとおりに入っている。〔検証: 自動テスト〕
2. **A3 ロールの値**: 保存された対話ログの各発言の `role` は、ユーザーの発言なら `user`、AI の応答なら `assistant` で、それ以外の値はない。〔検証: 自動テスト〕
3. **A4 識別子**: 保存された対話ログの JSON と `dialog_logs` の列から、participant_id、講義ID、学習セッションID、対話セッションID の4つを読み取れ、それぞれが、保存要求の participant_id、その参加者に対応する講義、`learning.db` の学習セッション、`tutor.db` の対話セッションに一致する。JSON と列の値は一致する。〔検証: 自動テスト〕
4. **A5 発言の時刻**: 保存された対話ログの各発言に `timestamp` がある。ユーザーの発言の時刻は、サーバーがその発言を受け付けた時刻である。AI の応答の時刻は、その応答の生成を終えた時刻であり、応答の生成に時間がかかった場合(受け付けから生成終了までの間に時刻が1秒以上進んだ場合)、対応するユーザーの発言の時刻より後になる。この変更の前に保存された AI の応答(生成を終えた時刻の記録がないもの)の `timestamp` は `null` であり、時刻の値(対応するユーザーの発言の時刻を含む)にはならない(N3)。時刻の値は、共有IF の「時刻の形式」に従う。〔検証: 自動テスト(時刻を制御して確認。記録なしの場合は、変更前の形で保存された AI の応答を用意して確認)〕
5. **A6 チューターの内部判断**: 保存された対話ログの AI の応答には、`utterance_type`、`dialogue_move`、`interpretation_state` があり、その値は、1往復ごとに `tutor.db` の `messages` に保存された値と一致する(`interpretation_state` は、`messages` の値を JSON として解釈したものと等しい。`messages` の値が空なら `null`)。ユーザーの発言には、この3つのキーがない。〔検証: 自動テスト〕
6. **A7 含めないもの**: 画面を開いたときの固定のあいさつは、保存された対話ログに含まれない。AI の応答の生成に失敗した往復(エラー表示と、そのときのユーザーの発言)も含まれない。〔検証: 自動テスト〕
7. **A8 終了時刻と終了の方法**: 保存された対話ログには、保存を受け付けた時刻が `ended_at` として、保存要求の `end_method`(`end_button` または `page_leave`)が `end_method` として入っている。〔検証: 自動テスト〕
8. **A11 二重保存しない**: 同じ参加者について保存要求を続けて2回送っても、`tutor.db` に保存されるその対話セッションの対話ログは1件だけである。1件であることは、`dialog_logs` の対話セッションIDが一意であること(DB の制約)で保証される。〔検証: 自動テスト(続けて2回の保存で1件であること、および同じ対話セッションIDの行を2つ作れないこと)〕
9. **A12 上書き**: 同じ対話セッションについて保存した後、発言が追加されてから再び保存すると、その対話セッションの対話ログは1件のままで、発言の並び、`ended_at`、`end_method` は2回目の保存の内容になっている。〔検証: 自動テスト〕
10. **A13 発言0件での保存**: その参加者がまだ1回も発言を送っていない状態(学習セッション・対話セッションが未作成の状態を含む)で保存要求を送ると、成功の応答が返り、`messages` が空の配列の対話ログが1件保存される。保存された対話ログからは、A4 と同じく4つの識別子を読み取れ、学習セッションID・対話セッションIDは、保存の時点で作られた `learning.db` の学習セッション・`tutor.db` の対話セッションに一致する。その後、同じ参加者が発言を送ると、その発言は同じ対話セッションに保存される(N2)。〔検証: 自動テスト〕
11. **A14 既存の保存と対話を壊さない**: 既存の自動テスト(`uv run pytest tests/ -v`、実 LLM を除く)がすべて成功する。`POST /chat` の応答の内容は、この変更の前と同じ。1往復ごとに、ユーザーの発言と AI の応答が `tutor.db` に保存されることも、この変更の前と同じ(AI の応答の生成を終えた時刻が追加で記録されることを除く)。〔検証: 自動テスト〕
12. **A15 変更前の DB でも動く**: この変更の前の形の `tutor.db`(`dialog_logs` がなく、`messages` に `responded_at` がなく、対話が保存済み)を使って起動しても、発言を送る、保存要求で保存する、のそれぞれが成功し、既存の `messages` の行の値は変わらない。保存した対話ログでは、変更前に保存された AI の応答の `timestamp` は `null` になり(A5、N3)、変更後に送った発言の AI の応答には、生成を終えた時刻が入る。〔検証: 自動テスト〕
13. **A17 保存 API の誤りと失敗**: 共有IF の「要求の誤り」のいずれかに当たる保存要求には状態 400 が返り、対話ログは保存・変更されない。DB に書けないときは2xx 以外の状態が返り、それまでに保存されていた対話ログは変更されない。〔検証: 自動テスト〕

## PBI-A-2: 終了ボタン、完了画面、失敗の表示、再訪(画面)

PBI-A-1 の後に着手する。PBI-A-1 の保存 API を使う。

### 実現内容(What)

対象は `/reflect` の画面の「AI チューター」の対話。

- AI チューターの欄の、メッセージ入力欄と送信ボタンの下に、「対話ログを送信して終了する」ボタンを置く。送信ボタンと見分けがつく見た目にする(Q11)。
- 押すと、終了の方法を「終了ボタン」として、その参加者の対話ログの保存を要求する(保存の内容は PBI-A-1)。
- AI の応答を待っている間(送信してから、応答またはエラーが表示されるまで)は、終了ボタンを押せない(F7)。応答またはエラーが表示されると、再び押せる。
- 保存が成功すると、画面は完了画面に切り替わる。完了画面では、対話ログを送信したことが表示され、メッセージの入力・送信と終了ボタンは使えない(Q5)。発言が0件のときも同じ(Q6)。
- 保存が失敗すると、失敗したことと、もう一度押せば保存し直せることが画面に表示され、完了画面には切り替わらず、研究協力者はもう一度押して保存し直せる(Q7)。研究者への連絡を促す文言は出さない(N5)。
- 完了画面の後(または PBI-B の離脱時の保存の後)に、同じ参加者が同じ URL を開き直すと、完了画面ではなく通常の対話の画面が表示され、再び対話できる。そこで送った発言は同じ対話セッションに追加され、もう一度終了ボタンを押すと、その対話セッションの対話ログは、過去の訪問の発言を含む最新の内容で上書きされる(N1、Q6)。再訪時に、過去の訪問の対話はチャット欄に表示しない(現状どおり。本仕様では画面の表示を変えない)(N7)。過去の対話の表示は、本仕様のスコープ外とする(必要なら別 Issue)。
- 「開き直す」は、URL を開く・再読み込みするなど、ページを新たに読み込む操作を指す。Safari の「戻る」「進む」で、以前の状態のページ(完了画面を含む)が復元される場合は、A16 の対象外とする(前提のブラウザの制約)。

## PBI-B: ブラウザを閉じるときの確認と、離脱時の保存

PBI-A-2 の後に着手する。PBI-A-1 の保存 API(`end_method` = `page_leave`)と、PBI-A-2 の画面(終了ボタンの保存の成否)を使う。サーバー側は変更しない。

### 実現内容(What)

**用語**

- **発言済み**: この画面を開いてから、1回以上発言を送信したこと。送信の操作は、送信ボタンを押すことと、入力欄で Enter キーを押すことの**どちらでもよい**(N8)。送信が行われない操作(空・空白だけの入力、IME の変換の確定の Enter、修飾キー付きの Enter、応答待ちの間の操作など。[reflect-chat-multiline-input.md](./reflect-chat-multiline-input.md) で送信しないと定めたもの)は数えない。AI の応答の成否(エラー表示になったかどうか)は問わない。過去の訪問での発言や、再読み込みの前の発言は数えない(N4)。
- **終了済み**: この画面で、終了ボタンによる保存が成功した(完了画面になった)こと。
- **離脱の確定**: タブ・ブラウザを閉じる、再読み込みする、別のページへ移動する、ブラウザの戻る、のいずれかで、ページから実際に離れることが決まったこと。確認のダイアログで「離れる」を選んだ場合と、確認のダイアログが表示されなかった場合の両方を含む。ダイアログで「キャンセル」を選んだ場合は、離脱は確定しない(F4)。

**振る舞い**

- 発言済みで、終了済みでない状態で、タブ・ブラウザを閉じる、再読み込みする、別のページへ移動する、ブラウザの戻る、のいずれかをしようとすると、ブラウザ標準の確認のダイアログの表示を求める(Q8、Q10)。文言とボタンはブラウザ標準のもので、ページ側では指定しない。ブラウザが表示しないと判断した場合は、表示されないことがある(前提のブラウザの制約)。
- 確認で画面に戻る(キャンセル)を選ぶと、画面はそのまま残り、対話を続けられる。このとき、離脱時の保存は行わない。
- **発言済みで、終了済みでない状態で、離脱が確定したとき**に、終了の方法を「離脱時」(`page_leave`)として、対話ログの保存を試みる(F4)。確認のダイアログで「離れる」を選んだ場合に限らず、確認のダイアログが表示されなかった場合や、再読み込みの場合も、発言済みであれば保存を試みる。
- **離脱時の保存は、完了を保証しない**(ブラウザが通信の完了を保証しないため。1往復ごとの保存は残っている)(Q8)。
- 確認の表示中の操作のロックは、ブラウザ側のロックで満たしたとみなす(Q8)。本 PBI で独自のロックは設けない。
- 終了済みの後は、閉じるときの確認を求めず、離脱時の保存もしない(終了ボタンの保存を「離脱時」で上書きしない)。
- 発言済みでない状態では、確認を求めず、離脱が確定しても離脱時の保存をしない(B2)。
- 離脱時の保存の後、または終了ボタンの保存の後に、同じ参加者が同じ URL を開き直した場合は、PBI-A-2 の再訪(A16、N1)と同じく再び対話できる。開き直した画面で送信すると、確認と離脱時の保存の条件(上記)が改めて当てはまる(N4)。

### 既知の限界(PO の決定 N9・N10。AC では保証しない)

- **複数タブ・複数端末での上書き(N9)**: 同じ参加者が別のタブ(または別の端末)でも同じ画面を開いている場合、一方のタブで終了ボタンの保存(`end_button`)をした後に、もう一方のタブで発言済みのまま離脱すると、離脱時の保存(`page_leave`)で上書きされる。サーバー側では防がず、最新の保存が残る(B6 は同じタブの中だけを対象にする)。発言の並びはどちらの保存でも同じ(DB の全発言)で、違うのは `end_method` と `ended_at` だけのため、発言の欠落は起きない。また、保存 API に認証はなく、participant_id を知っていれば誰でも保存を要求できる(対話の本文はサーバーが DB から作るため、内容の改ざんはできない。既存の `/chat` と同じ前提)。
- **終了ボタンの保存の応答が返る前の離脱(N10)**: 終了ボタンを押して、保存の応答が返る前にタブを閉じると、まだ終了済みではないため、確認のダイアログが出て、離脱が確定すると離脱時の保存も送られる。サーバーに後から届いたほうが残り、`end_method` が `end_button` と `page_leave` のどちらになるかは保証しない。発言の並びはどちらでも同じ。対話ログが残る可能性が高いほうを優先するため、終了ボタンの保存要求を送った時点で離脱時の保存を止めることはしない。

### スコープ外

- **保存が再デプロイ・再起動で失われない保存基盤(旧案の PBI-C)**: 別 Issue として起票する(PO の決定、Q2・分割)。**実験開始前までに完了していることが前提**。実施環境と実験開始日は未確認で、起票時に確認する。旧案の AC14(保存が消えない)は、この別 Issue の受入基準として扱い、本仕様の AC に含めない。
- 研究者が対話ログを取り出す方法(Issue 本文で別 Issue と明記)。
- `/lecture` の画面(対話がない)。
- LAD の表示データ(視聴ログ・小テスト)の保存形式の変更、および対話ログへの同梱(Q9)。
- `tutor.db` の `sessions.participant_id` が空文字で保存されている現状の修正(学習セッション経由でたどれるため)。
- 再訪時(同じ URL を開き直したとき)に、過去の訪問の対話をチャット欄に表示すること(N7。現状どおり表示しない。必要なら別 Issue)。
- スマートフォン・タブレット(Q12)。
- ブラウザ・OS の強制終了、PC のスリープ・電源断のときの保存(ダイアログも通信も起きないため。1往復ごとの保存で対話は残る)。
- 保存 API の認証(既存の `/chat` と同じく、認証を設けない)。
- 複数タブ・複数端末での上書きの防止(N9。許容し、既知の限界とする)。
