# DB の永続化 — 再デプロイ・再起動しても、協力者の学習データと対話データが失われない

## Issue

#29(要件: NFR-14、NFR-12、NFR-16。方式の決定: #28)

## 目的(Why)

研究者は、実験期間(2026年12月末まで)の途中で、修正のための再デプロイや、Cloud Run によるインスタンスの再起動に必ず出会う。現状の Cloud Run では、コンテナ内の SQLite(`learning.db` / `tutor.db`)が再デプロイ・再起動のたびに消える。データが消えると、協力者の視聴・小テスト・対話の記録が失われ、「有効な1人分のデータ」(プロダクトゴールの主指標)が成立しなくなる。協力者に同じ学習をやり直してもらうことはできない。

そこで、2つの SQLite を外部(GCS)へ継続して複製し、起動時に復元できるようにする。あわせて、バックアップから復元できる手順と、実験中にスキーマを変えないための注意を、研究者が参照できる形で残す。

## 実現内容(What)

### 1. 稼働中の継続複製

- Cloud Run で稼働している間、`learning.db` と `tutor.db` の両方の変更が、GCS のバケットへ継続して複製される。
- 複製先は2つの DB で分かれ、片方の復元がもう片方に影響しない。

### 2. 起動時の復元

- コンテナの起動時、アプリが要求を受け付ける前に、2つの DB をそれぞれ GCS の複製から復元する。
- 複製がまだ存在しない DB(初回デプロイ)は、新規に作成する(現状どおり、アプリがスキーマを適用する)。
- 複製が存在するのに復元に失敗したとき(権限不足、通信失敗など)は、**空の DB で起動しない**。起動を失敗させ、ログに原因を残す。空の DB で起動すると、その空の状態が新しい複製として上書き・優先され、データが失われたのと同じになるため。
- 複製先の設定がないまま起動したときは、起動を失敗させ、ログに「複製先の設定がない」ことを残す。Cloud Run での設定漏れで、永続化なしのまま稼働するのを防ぐため。
- ローカルで複製なしに動かしたいときは、「複製しない」ことを明示に指定した場合に限り、複製・復元をせずにアプリを起動する。指定の方法は README に書く。
- 起動時に DB へ書き込む処理(スキーマの適用など)は、すべて2つの DB の復元が終わった後に動く。復元より前に書き込むと、その内容は復元で失われる。
- 起動の手順は、2つの DB の復元の後、Litestream の複製とアプリの起動の前に、2つの DB を WAL モードにする(Q10 の決定)。複製がない初回も、アプリの起動の前に2つの DB が WAL モードになっている。
- 起動の手順が読む環境変数の名前は、本仕様で固定する(Litestream の設定、起動の手順、テスト、README が共有する約束。task-splitter と implementer は名前を変えない。変えるときはレベル2):

  | 環境変数 | 意味 | 値 |
  |---|---|---|
  | `DB_REPLICA_BUCKET` | 複製先の GCS バケット名(`gs://` を付けない名前だけ)。2つの DB は、このバケットの中で別々の場所に複製される | バケット名。未設定または空は「複製先の設定がない」 |
  | `DB_REPLICA_DISABLED` | 「複製しない」の明示の指定(ローカル用) | `1` のときだけ有効。それ以外の値と未設定は「指定なし」 |

  - `DB_REPLICA_DISABLED=1` のときは、`DB_REPLICA_BUCKET` の有無にかかわらず、復元・複製をせずにアプリを起動し、複製しないことをログに残す。
  - 名前は提案(feasibility の F3 を受けて、本仕様の起草者が付けた)であり、仕様の承認で確定する。
- 起動の手順に、#30 のための段(ユーザー登録・初期化)は設けない(Q7 は解消)。起動の手順は、アプリに渡された環境変数(`SECRET_KEY`、#30 の資格情報の設定ファイルの場所など)を変えずにアプリへ渡す。

### 3. 停止時の最終同期

- Cloud Run が停止を通知(SIGTERM)したとき、未複製の変更を GCS へ送ってから終了する。
- アプリ(gunicorn)が停止の通知の後に処理中の要求を待つ時間(終了猶予)は、Cloud Run の停止の猶予(10秒。(未確認: 公式ドキュメント未確認))より短くする。既定の 30 秒のままだと、処理中の要求を待つ間に猶予を使い切り、最終同期の前にコンテナが強制終了されうるため。
- その結果、停止の通知の時点で処理中の要求(AI の応答の待機など)が終了猶予の内に終わらないときは、その要求は打ち切られる。計画された再デプロイは協力者が使っていない時間帯に行う(Q1 の決定)ため、主に計画外の停止で起こる。
- 待ち時間の設計値: アプリ(gunicorn)の終了猶予は約4秒、Litestream の最終同期の待ち(`shutdown-sync-timeout`)は約5秒とする(既定はどちらも30秒で、猶予を超える。Cloud Run が SIGTERM から10秒で強制終了することは、feasibility-29 が公式ドキュメント(container-contract)で確認済み)。値の実測は AC11(PO確認)で行う。
- 打ち切られた AI 応答の往復は保存されず、協力者の画面には失敗としてエラーが出る(許容損失として PO決定済み、F5)。
- Litestream が、アプリ(子のプロセス)の終了を待ってから最終同期するのか、同期を先に始めるのかは、公式ドキュメントで確かめられていない(U2)。AC11 の実測で、停止の通知から最終同期の完了までの秒数を記録する。

### 4. バックアップと復元の手順

- GCS バケットは、リージョン `asia-northeast1` に置き、オブジェクトのバージョニングと、ライフサイクルで「古い世代を 30 日後に削除」する設定を持つ。バケットの保持ポリシー(ロック)は設定しない。
- 2026年12月末の実験終了後の複製(と世代)の扱いは、研究室が倫理審査の条件(#38)を見て手動で判断することを、README に書く。
- **Litestream の世代管理(retention)と、バケットの 30 日のライフサイクルの関係**:
  - Litestream 0.5 系は、自ら複製先の古いファイルを消す世代管理(retention)を持ち、無効にもできる(v0.5.8 以降。無効にした場合は、古いファイルの削除をバケットのライフサイクルに任せることが文書で想定されている)。〔確認: 公式ドキュメント(feasibility-29、2026-10-26)〕
  - バケットのライフサイクルが消すのは「最新でない世代」(上書き・削除された後の古い版)だけで、最新の版は消さない。Litestream が今使っている複製のファイルは最新の版なので、ライフサイクルで消えない見込み。(未確認: Litestream が複製のファイルを上書きするか、新しい名前で足していくかを確かめていない)
  - retention は有効のまま(既定)とする(Q12 の決定)。Litestream が古いファイルを消すので、バケットにはその削除の権限が要り、Q5 の決定の `roles/storage.objectAdmin` で足りる。
  - 古い世代が消えた後に、最新の状態を復元できることを検証する(U9、AC13)。
- Cloud Run は、実行サービスアカウントの ADC で GCS に書く。鍵ファイルは使わない。権限は、対象のバケットだけに `roles/storage.objectAdmin` を付ける(プロジェクト全体には付けない。Q5 の決定)。
- 研究者が、GCS の複製から、任意の環境(手元の PC など)に2つの DB を復元する手順が README にある。
- #25 の研究者ダウンロード(対話ログの JSON)を、対話ログの手動バックアップとして併用する手順(計画された再デプロイの直前に取る)が README にある。

### A. 自動テスト(設定・起動手順。Litestream と GCS がなくても実行できる)

1. **複製の対象**: Litestream の設定に、`learning.db` と `tutor.db` の2つが、それぞれ GCS の複製先とともに定義されている。設定の DB のパスは、コンテナ内でアプリが使う `LEARNING_DB_PATH` / `TUTOR_DB_PATH` の値と一致する。〔検証: 自動テスト〕
2. **起動の順序**: 起動手順を、`litestream` を模したコマンドで実行したとき、2つの DB の復元が両方とも終わってから、アプリ(gunicorn)の起動が始まる。〔検証: 自動テスト(起動手順がシェルスクリプトの場合、bash が要る)〕
3. **復元の失敗時に空で起動しない**: 模したコマンドで、どちらか一方の DB の復元を失敗させたとき、起動手順は 0 以外の終了コードで終わり、アプリは起動しない。〔検証: 自動テスト(同上)〕
4. **複製がない初回**: 模したコマンドで「複製なし」を返したとき、起動手順はアプリを起動し、アプリの起動後に2つの DB がスキーマ適用済みで存在する。〔検証: 自動テスト(同上)〕
5. **複製先の設定がないときは起動しない**: `DB_REPLICA_BUCKET` を与えず(または空にし)、`DB_REPLICA_DISABLED=1` も与えずに起動手順を実行したとき、起動手順は 0 以外の終了コードで終わり、アプリは起動せず、出力に複製先の設定がないことが示される。`DB_REPLICA_DISABLED=1` で実行したときは、復元・複製を行わずにアプリが起動する。〔検証: 自動テスト(同上)〕
6. **WAL での動作**: あらかじめ WAL モードにした2つの DB に対して、アプリの起動(スキーマ適用)と、学習データ・対話データの書き込み・読み出しを行うと、既存のテストと同じ結果になり、その後も2つの DB のジャーナルモードは `wal` のままである。〔検証: 自動テスト〕
   - 注: 稼働中(Litestream が複製している間)のジャーナルモードが `wal` であることは、この AC では確かめない。AC8(往復)で確かめる。起動の手順が WAL にすることは AC21 で確かめる(Q10 の決定)。
7. **既存の挙動の回帰**: `uv run pytest tests/ -v` が、変更前と同じく全件成功する(`real_llm` を除く)。〔検証: 自動テスト〕
21. **起動の手順による WAL 化**: 起動の手順を、`litestream` を模したコマンド(AC2 と同じ)で実行したとき、(a) 復元で WAL でない(`delete` の)2つの DB が置かれた場合と、(b)「複製なし」の場合の両方で、アプリの起動が始まる時点で、2つの DB のジャーナルモードが `wal` である。ジャーナルモードは、模したものではない実際の SQLite(例: Python 標準の `sqlite3`)で DB ファイルを開いて確かめる。起動の手順が WAL にする処理にも、偽の SQLite を使わない(模してよいのは `litestream` とアプリの起動だけ)。〔検証: 自動テスト(起動手順がシェルスクリプトの場合、bash が要る)〕
   - 番号は、既存の AC の番号を変えないよう 21 とした(Q10 の決定で追加)。

### F. Docker のビルドの中の自動確認(SQLite の WAL-reset の不具合(U8)を受けて追加。Q11 の決定)

   - 注: Litestream(v0.5.17)が使う SQLite の版は、この AC の対象外とし、未確認のまま残す(U8)。
