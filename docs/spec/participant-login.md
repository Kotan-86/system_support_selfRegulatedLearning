# 研究協力者のログイン — ID/パスワードでログインし、本人のデータだけを扱える

## Issue

#30(関連要件: FR-50、FR-51、FR-52、NFR-08。関連: FR-53、FR-54、NFR-05、NFR-06)、#31(ID 発行の上限を31件に変更)

## 目的(Why)

現状は、URL のクエリ(`?participant_id=1`)や要求本文の `participant_id` を書き換えるだけで、誰でも他人の学習ログ・対話ログを読み、書き込める。実験では最大30人の研究協力者が同じシステムを使うため、他人のデータの閲覧や、なりすましによる記録の混入が起きると、情報漏洩になり、研究データの信頼性(「有効な1人分のデータ」の判定)も損なわれる。

そこで、研究者が発行した ID/パスワードでログインした人だけが画面と API を使えるようにし、参加者を、ログインしたセッションから特定する。パスワードは平文で保存しない。

## 実現内容(What)

### 1. ログインとログアウト

- ログイン画面がある。ID とパスワードを入力して送ると、正しい組み合わせで、かつ状態が「有効」の ID のときだけログインできる。
- ログインに失敗したときは、HTTP 401 で、ログイン画面を同じ失敗の文言つきで再表示する。「ID が存在しない」「パスワードが違う」「ID が停止されている」を区別しない(ステータスも文言も同じ)。
- 画面のリダイレクト(未ログインの画面からログイン画面へ、ログイン後・ログアウト後の移動、ログイン済みの `/` とログイン画面から `/lecture` へ)は、HTTP 302 で行う。
- ログインに成功すると、未ログインのときに開こうとした参加者の画面(`/lecture` または `/reflect`)へ移る。開こうとした画面がない(ログイン画面を直接開いた)ときは、`/lecture` へ移る。移動先は、このサイト内の参加者の画面に限る。
- 参加者の画面(`/lecture`、`/reflect`)に、ログアウトの操作がある。ログアウトすると、そのブラウザのログイン状態が消え、ログイン画面に戻る。
- ログインしたまま、ログイン画面または `/` を開いたときは、`/lecture` へ移る。

### 2. 未ログインの要求の拒否(FR-51)

- ログインしていない要求は、次を除き、すべて拒否する。拒否した応答に、学習データ・対話データを含めない。
  - 除外: ログイン画面、ログインの送信、画面の静的ファイル(CSS・JS)、研究者向けの `/research/` 配下(別系統の Basic 認証のまま。参加者のログインを要求せず、受け付けもしない)
- 画面(`/`、`/lecture`、`/reflect`)は、ログイン画面へリダイレクトする。
- API(`/chat`、`/api/` 配下)は、HTTP 401 を返す。DB に書き込まない。

### 3. 参加者の特定(FR-52)

- 参加者は、ログインした ID で決まる。画面と API は、ログインした本人のデータだけを読み書きする。
- 画面は、クエリの `participant_id` を無視し、ログインした本人の画面を表示する。画面の「参加者 ID」には、ログインした ID を表示する。
- API にクライアントが送る `participant_id`(本文・クエリ・URL のパス)は、次のとおり扱う。
  - 送られていない: ログインした本人として処理する。
  - 本人の ID と一致する: そのまま処理する。
  - 本人の ID と異なる: HTTP 403 で拒否する。2つの DB のどこにも記録せず(本人の分も記録しない)、他人のデータを返さない。`POST /chat` では AI(LLM)を呼ばない。
  - 値の形による扱い(本文・クエリ): 空文字と `null` は「送られていない」と同じに扱う。数値は、10進の文字列にしてから本人の ID と比べる(例: `1` は `"1"`)。真偽値は数値に含めない。文字列・数値・`null` 以外(真偽値、配列、オブジェクト)のときは、HTTP 400 で拒否し、2つの DB のどこにも記録しない(既存の検証のエラーと同じ値)。
  - 空白だけの文字列(例: `"  "`)は「送られていない」に含めず、本人の ID と異なる値として HTTP 403 で拒否する。数値を文字列にした結果が本人の ID と異なるもの(例: `1.0` は `"1.0"` となり、`"1"` と一致しない)も、HTTP 403 で拒否する。
- `POST /chat` の `session_id` が、ログインした本人の対話セッションでないときは、存在しないセッションと同じ応答(HTTP 404)で拒否する。他人の対話セッションに書き込まない。
- `lecture_id`(どの講義か)は参加者の識別ではないため、本 PBI では現状のまま扱う。(#34 で、選択と異なる値は 403、未選択は 409 などに変わった。lecture-selection.md の What 4節)

### 4. 講義割当の維持

> **置き換え(#34、[lecture-selection.md](./lecture-selection.md) の What 3節・4節、AC1・16)**: 固定マップによる講義割当は廃止した。参加者の講義は、協力者が選択の画面で選んだ講義(保存された選択)で決まり、未選択でログインすると選択の画面へ移る。以下の記述は、#30 の時点の内容の記録であり、現行の挙動ではない。

- ログイン ID を、そのまま学習データの参加者 ID として使う(既存の DB の列を変えない)。講義割当は、現状の固定マップの規則のまま維持する。`P01`〜`P31` はマップにないため、`lecture_id` の指定がなければ全員 lecture-1 になる。協力者が講義を選ぶ仕組みは別 Issue で扱う。

### 5. ID/パスワードの登録(研究者)

- 研究者は、作成スクリプトで参加者の ID を登録する。ID は、スクリプトが `P01` から順に、未使用の次の番号を払い出す(研究者は ID を指定しない)。`P31` の次は払い出さない(32件目の登録は拒否する。停止中の ID も件数に数える)。31件の内訳は、協力者30件と研究者確認用1件(`P01`)。
- スクリプトは、16文字以上のランダムなパスワードを生成し、その場で1回だけ端末に表示する。研究者は、それを協力者へ配布する。
- 例外: 一括発行(`bulk-add`)は、パスワードを端末に表示せず、配布用の CSV に書く(#31。詳細は [participant-bulk-issuance.md](./participant-bulk-issuance.md))。1件ずつの登録・再発行は、上の規則のまま。
- 登録した内容は、設定ファイルに書かれる。設定ファイルは、資格情報の正であり、研究者が一目で把握する台帳を兼ねる。項目は、ID ごとに、ID・発行日(再発行したら更新日)・状態(有効/停止)・備考(任意)・パスワードのハッシュ。平文のパスワード、氏名など個人を特定する情報、講義割当は書かない。
- 登録済みで状態が「有効」の ID を指定して再発行を指示すると、新しいパスワードが生成され、古いパスワードではログインできなくなる(反映は、下記の本番への反映の後)。状態が「停止」の ID の再発行を指示すると、スクリプトは失敗を示して終わり、設定ファイルを変えない(停止の解除と混同しない)。
- 研究者は、登録済みの ID を指定して、作成スクリプトに停止を指示する。停止すると、設定ファイルのその ID の状態が「停止」になり、更新日が停止した日になる。その ID のハッシュと、他の ID の項目は変わらない。研究者は設定ファイルを手で書き換えない。
- 状態が「停止」の ID は、正しいパスワードでも、新しくログインできない(反映は、下記の本番への反映の後。発行済みのセッションは、有効期限まで残る)。停止した ID の番号は、新規の登録で再利用しない。停止を解除して「有効」に戻す指示は設けない(範囲外。必要なら新しい ID を払い出す)。
- アプリ(ログインの照合)は、ID の形式(`P01`〜`P31`)を確かめない。設定ファイルにある ID なら、形式によらず照合する。形式の強制は、作成スクリプトの払い出しだけで行う。
- アプリは、起動時に設定ファイルを読む。設定ファイルの場所が指定されていない、指定の場所にファイルがない、読めない、または形式が壊れている(内容を解析できない、ID の項目に必須の項目が欠けている、状態が「有効」「停止」以外、同じ ID が2回現れる)ときは、アプリが起動しない(起動時に、原因と、設定ファイルの場所を指定する環境変数の名前を示すエラーで止まる)。形式が正しければ、ID が0件の設定ファイル(登録前の状態)と、全員が「停止」の設定ファイルでも、アプリは起動する(壊れているとみなさない。全員が「停止」なら、誰も新しくログインできない)。テスト・ローカルの実行・#29 の起動手順でも、設定ファイルの指定が要る。
- 設定ファイルはリポジトリに入れず(`.gitignore` で除外する)、コンテナのイメージにも含めない。研究者の手元と、Secret Manager のシークレットにだけ置く。
- 本番への反映: 研究者は、更新した設定ファイルを Secret Manager のシークレットの新しい版として登録し、Cloud Run を再デプロイする。アプリは、Secret Manager から渡された設定ファイルの内容で照合する。手順は README に書く。

### 6. セッションの安全性の設定

- `SECRET_KEY` が設定されていない、空、または以前の既定値(`tutor_secret_key`)のときは、アプリが起動しない(起動時に、`SECRET_KEY` を設定するよう示すエラーで止まる)。テスト・ローカルの実行でも設定が要る。
- セッション Cookie は、JavaScript から読めず(`HttpOnly`)、他サイトからの POST に付かない(`SameSite=Lax`)。既定で `Secure` を付ける。ローカルの HTTP で動かすときだけ、環境変数の指定で `Secure` を外せる。その方法を README に書く。
- ログインの有効期限は、ログインした時刻から12時間。要求のたびに延長しない。12時間を過ぎたら再ログインを求める。

## 受入基準

AC の番号は、前版からの参照を保つため、追加した AC を末尾の番号(24〜30)で各節に置いた。

テストの参加者 ID: アプリは ID の形式を確かめないため、AC1〜16・20〜22・24・27・28・30 は、テスト用の設定ファイルに `P01` 形式でない ID(例: `1`、`A`、`B`)を入れて検証してよい。AC25 だけは `P01` 形式の ID で検証する。

### A. ログイン・ログアウト

1. **正しい資格情報**: 登録済みで状態が「有効」の ID とそのパスワードでログインを送ると、ログインが成立し、続けて `/lecture` を開くと、その ID の講義画面が 200 で表示され、画面の「参加者 ID」にその ID が表示される。〔検証: 自動テスト〕
2. **誤った資格情報**: 登録済みの ID と誤ったパスワード、未登録の ID、空の ID、空のパスワードのそれぞれでログインを送ると、ログインは成立せず(続く `/lecture` はログイン画面への 302 のリダイレクト)、4つの応答はいずれも HTTP 401 で、ログイン画面が失敗の文言つきで再表示され、その文言は4つで同一である。〔検証: 自動テスト〕
3. **再発行後の旧パスワード**: ある ID のパスワードを再発行し、更新後の設定ファイルでアプリを起動すると、古いパスワードではログインできず、新しいパスワードではログインできる。〔検証: 自動テスト〕
4. **ログイン後の移動先**: 未ログインで `/reflect` を開いてログイン画面へ移り、そこでログインすると `/reflect` が表示される。ログイン画面を直接開いてログインすると `/lecture` が表示される。移動先にサイト外の URL を指定しても、サイト外へは移らない。〔検証: 自動テスト〕
5. **ログアウト**: ログイン後にログアウトすると、続く `/lecture` はログイン画面へリダイレクトされ、`/api/last-updated` は 401 になる。〔検証: 自動テスト〕
6. **画面の操作**: ブラウザでログイン画面から ID/パスワードを入力してログインし、講義画面 → 小テスト → 振り返り画面(AI チューターとの対話、LAD の表示、終了ボタンによる対話ログの保存)を、URL に `participant_id` を付けずに一通り使える。ログアウトの操作でログイン画面に戻り、戻るボタンで前の画面を開いても、データが表示されない(ログイン画面になる)。誤ったパスワードでは失敗の文言が表示される。〔検証: PO確認〕
24. **ログイン済みの `/` とログイン画面**: ログインした状態で `/` を開くと `/lecture` へリダイレクトされる。ログインした状態でログイン画面を開くと `/lecture` へリダイレクトされる。〔検証: 自動テスト〕
27. **停止した ID**: 状態が「停止」の ID と、その正しいパスワードでログインを送ると、ログインは成立せず、AC2 と同じ HTTP 401 と同じ失敗の文言(ログイン画面の再表示)になる。停止の前に登録した正しいパスワードでも、同じ結果になる。〔検証: 自動テスト〕

### B. 未ログインの拒否(FR-51)

7. **画面**: ログインしていない状態で `/`、`/lecture`、`/reflect`、`/lecture?participant_id=1`、`/reflect?participant_id=1` を開くと、5つとも HTTP 302 で、移動先(`Location`)がログイン画面である。応答に参加者のデータを含まない。〔検証: 自動テスト〕
8. **API**: ログインしていない状態で、`POST /chat`、`POST /api/dialog-log`、`POST /api/quiz-attempts`、`POST /api/viewing-log`、`GET /api/last-updated?participant_id=1`、`GET /api/participants/1/lad` を呼ぶと、すべて 401 になり、2つの DB の行数が呼ぶ前と変わらない。`POST /chat` では、AI(LLM)の呼び出しが起きない。〔検証: 自動テスト〕
9. **除外の範囲**: ログインしていない状態で、ログイン画面と画面の静的ファイル(例: `/static/js/common/api_client.js`)は 200 で取得できる。〔検証: 自動テスト〕
10. **研究者の経路は不変**: 研究者向けの `/research/` 配下は、参加者のログインの有無によらず、従来どおり Basic 認証だけで判定される(既存の `tests/test_api/test_research_dialog_download_api.py` がすべて成功する。参加者としてログインした状態でも、Basic 認証なしでは 401 になる)。〔検証: 自動テスト〕

### C. 本人のデータだけを扱う(FR-52、NFR-08)

11. **クエリなしの画面**: ID `A` でログインした状態で、`participant_id` を付けずに `/lecture` と `/reflect` を開くと、`A` の画面が 200 で表示される。〔検証: 自動テスト〕
12. **他人の ID を指定した書き込み**: ID `A` でログインした状態で、本文の `participant_id` を `B` にして `POST /api/viewing-log`、`POST /api/quiz-attempts`、`POST /api/dialog-log`、`POST /chat` を送ると、4つとも HTTP 403 になる。2つの DB の行数は、呼ぶ前と変わらない(`A` の分も `B` の分も増えず、既存の行も変わらない)。`POST /chat` では、AI(LLM)の呼び出しが起きない。〔検証: 自動テスト(LLM は偽物に差し替える)〕
13. **他人の ID を指定した読み出し**: `B` に視聴ログと小テストの記録がある状態で、ID `A` でログインし、次を開く。〔検証: 自動テスト〕

    - `/reflect?participant_id=B`、`/lecture?participant_id=B`: どちらも 200 で `A` の画面が表示され、画面の「参加者 ID」は `A` である。応答に `B` の ID とデータが含まれない。
14. **participant_id の省略**: ID `A` でログインした状態で、本文・クエリに `participant_id` を含めずに、各書き込み API と `GET /api/last-updated` を呼ぶと、`A` のデータとして記録・取得される(従来の「未指定なら null」ではなく、`A` の最終更新時刻が返る)。〔検証: 自動テスト〕
15. **他人の対話セッション**: `B` の対話セッションがある状態で、ID `A` でログインし、`POST /chat` の `session_id` に `B` のセッション ID を入れて送ると、存在しないセッション ID を送ったときと同じステータス(HTTP 404)で拒否され、`B` のセッションのメッセージ数は変わらない。〔検証: 自動テスト(LLM は偽物に差し替える)〕
16. **本人の正常系の回帰**: ログインした状態で、既存の API テストが確かめている本人の操作(視聴ログ・小テストの記録、LAD の取得、対話、対話ログの保存と再訪時の扱い)の結果が、ログイン導入前と同じになる(既存の `tests/test_api/`、`tests/test_chat_lad/` を、ログインした状態で実行して成功する)。〔検証: 自動テスト〕
25. **講義割当の維持**(置き換え(#34): lecture-selection.md の AC16 に置き換えた。`P01` などで選択をせずにログインすると、選択の画面へ移り、lecture-1 の画面にならない。以下は #30 の時点の内容の記録): `P01`、`P02`、`P03`、`P30`、`P31` のそれぞれでログインし、`lecture_id` を指定せずに `/lecture` を開くと、どれも lecture-1 の講義画面になる。`lecture_id` を指定したときは、従来どおり指定の講義になる。〔検証: 自動テスト〕
30. **participant_id の値の形**: ID `1` でログインした状態で、本文の `participant_id` を、空文字、`null`、数値の `1` にして `POST /api/viewing-log` を送ると、3つとも `1` のデータとして記録される。数値の `2` にして送ると、HTTP 403 になり、2つの DB の行数は変わらない。`GET /api/last-updated?participant_id=`(空の値)は、`1` の最終更新時刻を返す。本文の `participant_id` を、真偽値の `true`、配列 `["1"]`、オブジェクト `{"id": "1"}` にして `POST /api/viewing-log` を送ると、3つとも HTTP 400 になり、2つの DB の行数は変わらない。本文の `participant_id` を、空白だけの文字列 `"  "`、数値の `1.0` にして `POST /api/viewing-log` を送ると、2つとも HTTP 403 になり(AC12 と同じ扱い)、2つの DB の行数は変わらない。〔検証: 自動テスト〕

### D. パスワードの保存と ID の登録(NFR-08)

17. **平文を保存しない**: 作成スクリプトで ID を登録した後、設定ファイル(資格情報の正)と2つの DB のどこにも、生成されたパスワードの文字列が含まれない。設定ファイルに保存されたハッシュで、生成されたパスワードを照合でき、別の文字列は照合に失敗する。設定ファイルの各 ID の項目は、ID・発行日(または更新日)・状態・備考・ハッシュだけである。〔検証: 自動テスト〕
18. **パスワードの表示**: 作成スクリプトは、生成したパスワードを実行時の出力に1回だけ表示する。生成されるパスワードは、毎回異なり、16文字以上である。〔検証: 自動テスト〕
19. **登録の上限と再発行の対象**: `P01`〜`P31` の31件が登録済みの状態で新規の登録を指示すると、スクリプトは失敗を示して 0 以外の終了コードで終わり、設定ファイルは変わらない(登録件数は31のまま。`P32` は払い出されない)。31件のうち一部の状態が「停止」でも、同じく失敗する(停止中の ID も件数に数える)。未登録の ID を指定して再発行を指示すると、スクリプトは失敗を示して 0 以外の終了コードで終わり、設定ファイルは変わらない。状態が「停止」の ID を指定して再発行を指示したときも、同じく失敗を示して 0 以外の終了コードで終わり、設定ファイルは変わらない(その ID の状態は「停止」、ハッシュは停止前のまま)。再発行では、指定した ID 以外のハッシュは変わらない。〔検証: 自動テスト〕
26. **ID の払い出し**: 登録が0件の設定ファイルに対して新規の登録を3回指示すると、`P01`、`P02`、`P03` が順に払い出される。状態を「停止」にした ID があっても、次の新規の登録は、払い出し済みの最大の番号の次になる(停止した番号を再利用しない)。〔検証: 自動テスト〕
29. **停止の指示**: `P01`〜`P03` が「有効」で登録済みの設定ファイルに対し、作成スクリプトに `P02` の停止を指示すると、0 の終了コードで終わり、`P02` の状態が「停止」、更新日が実行した日になる。`P02` のハッシュと、`P01`・`P03` の項目は変わらない。その設定ファイルでアプリを起動すると、`P02` は AC27 のとおりログインできず、`P01`・`P03` はログインできる。未登録の ID(例: `P04`)の停止を指示すると、失敗を示して 0 以外の終了コードで終わり、設定ファイルは変わらない。停止した `P02` の再発行を指示すると、AC19 のとおり失敗し、設定ファイルは変わらず、`P02` は引き続きログインできない。作成スクリプトに、`P02` を「有効」に戻す指示はない(停止の解除は範囲外)。〔検証: 自動テスト〕

### E. セッションの設定

20. **SECRET_KEY**: `SECRET_KEY` が未設定、空、または `tutor_secret_key` のとき、アプリの生成は失敗し、エラーの文言に `SECRET_KEY` が含まれる。設定されていれば起動する。〔検証: 自動テスト〕
21. **Cookie の属性**: ログインの成功の応答で発行されるセッション Cookie に、`HttpOnly` と `SameSite=Lax` が付く。`Secure` は、環境変数の指定がない既定の状態で付き、README に書く環境変数でローカル用に外したときだけ付かない。Cookie の値に、パスワードとそのハッシュが含まれない。〔検証: 自動テスト〕
28. **設定ファイル**: `SECRET_KEY` を設定した状態で、次の5つのそれぞれのとき、アプリの生成は失敗し、エラーの文言に、設定ファイルの場所を指定する環境変数の名前が含まれる: 場所の環境変数が未設定、指定の場所にファイルがない、指定の場所がディレクトリ(読めない)、内容を解析できない、ID の項目に必須の項目(ID・状態・ハッシュのいずれか)が欠けている。形式が正しい設定ファイルを指定すれば起動する。形式が正しく、ID が0件の設定ファイル、および全員の状態が「停止」の設定ファイルでも、アプリの生成は成功する(後者では、どの ID も AC27 のとおりログインできない)。〔検証: 自動テスト〕
22. **有効期限(12時間)**: ログインした時刻から11時間59分の時点では、`/lecture` は 200、`/api/last-updated` は 200 になる。ログインした時刻から12時間1分の時点では、`/lecture` はログイン画面へリダイレクトされ、`/api/last-updated` は 401 になる。途中に要求があっても、期限はログインした時刻から数える。〔検証: 自動テスト(時刻を進める)〕

### F. ドキュメント

23. **README**: README に、`SECRET_KEY` が必須であること、Cookie の `Secure` をローカルで外す方法、ID の登録(`P01`〜`P31` の払い出し)・再発行・停止・配布の手順、設定ファイルの扱い(項目、置き場、リポジトリにもイメージにも入れないこと)、Secret Manager への登録と再デプロイによる本番への反映手順、ログインしてから使う手順、ローカル実行に `SECRET_KEY` と設定ファイルの指定が要ることとその用意の仕方がある。`.env.example` に、`SECRET_KEY`・設定ファイルの場所・ローカル用に `Secure` を外す環境変数の項目があり、秘密の値を含まない。`SECRET_KEY` を「推奨」「未設定時は開発用デフォルト」とする記述と、`/lecture?participant_id=1` を利用の手順として案内する記述が残っていない。〔検証: AI実行〕

## 範囲外

- DB のスキーマの変更(ユーザーの表は作らない)。
