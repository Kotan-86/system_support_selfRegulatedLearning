# 協力者の ID/パスワードの一括発行 — 協力者30人分の台帳と配布用 CSV を一度に作り、確認専用 ID で本番の通しログインを確かめる

## Issue

#31(関連要件: FR-54、NFR-08、NFR-43。前提の仕様: [participant-login.md](./participant-login.md) の「5. ID/パスワードの登録(研究者)」、#30)

## 目的(Why)

実験開始(2026-10-27)に向けて、研究者は最大30人の研究協力者へ ID/パスワードを配る。#30 の作成スクリプトは1回の実行で1件だけ登録し、パスワードを端末に1回だけ表示する。30件を手で30回実行して表示を書き写すと、写し間違い・取りこぼし(表示を見逃すと後から確認できず、再発行が要る)・途中で止まったときの台帳と配布物の食い違いが起きやすい。配布に失敗した協力者はログインできず、「有効な1人分のデータ」(プロダクトゴールの主指標)を失う。

また、#30 の README の本番反映の手順には、Cloud Run のシークレットのマウント書式などが「(未確認)」のまま残っている。実験の前日に、発行した ID で本番にログインできることを通しで確かめておかないと、当日に協力者が誰もログインできない事態を防げない。確認に協力者用の ID を使うと、その ID の研究データに確認の記録が混ざるため、確認専用の ID を1つ設け、確認後に停止する。そのために、登録の上限を、協力者30人分に確認専用の1件を足した31件にする。

そこで、(1) 必要な件数を一度に登録し、(2) 配布しやすい CSV を秘密の除外の内に得て、(3) 確認専用の ID で本番の発行からログインまでを確かめる手順を、#30 の仕組み(設定ファイルを資格情報の正とし、Secret Manager と再デプロイで反映)を変えずに足す。

## 実現内容(What)

### 1. 一括発行

- 研究者は、作成スクリプトに、件数を指定して一括の新規登録を指示できる。件数の指定は必須。
- スクリプトは、`add` と同じ規則(払い出し済みの最大の番号の次から順に、停止した番号を再利用しない)で、指定した件数の ID を払い出し、それぞれに16文字以上のランダムなパスワードを生成し、ハッシュだけを設定ファイルに書く。既存の登録済みの件(有効・停止)の項目は変わらない。
- 一括の指示は「全部成功するか、何も変えないか」のどちらかで終わる。次のときは、失敗を示して 0 以外の終了コードで終わり、設定ファイルを変えず、CSV を残さず、パスワードを1件も出力しない: 登録済みの件数(停止を含む)と指定の件数の合計が上限(31)を超えるとき、件数の指定がない・正の整数でないとき、設定ファイルが壊れているとき、同名の CSV がすでにあるとき、設定ファイルまたは CSV の書き込みに失敗したとき。一部の件だけが登録された状態や、台帳と CSV の片方だけが書かれた状態を残さない。

### 2. 配布用の CSV

- 一括の指示が成功すると、払い出した ID ごとに、ID とパスワードの組を1件1行で書いた CSV ファイルができる。表計算ソフトで開いて、協力者ごとに切り分けられる。
- CSV の置き場は、設定ファイルと同じディレクトリで、ファイル名は決まった名前(`participants-distribution.csv`)。設定ファイルが既定の場所(`secrets/participants.json`)なら、CSV は `secrets/` の下にでき、リポジトリにもイメージにも入らない(既存の `.gitignore`・`.dockerignore` の除外の内)(Q7=案A、解決済み)。
- CSV の形式: 見出し行 `id,password` のあとに、払い出した順に1件1行。文字コードは UTF-8(BOM なし)(Q3、解決済み)。
- 同名の CSV がすでにあるときは、上書きせずに失敗する(前回の配布物を失わない。配布が済んだ CSV を削除するまで、次の一括発行はできない)。
- 端末(標準出力・標準エラー)にはパスワードを出さない。成功したときは、CSV の場所と件数を出す。
- 平文のパスワードは、設定ファイル(台帳)と2つの DB のどこにも書かない(#30 の AC17 のまま)。CSV にだけ、NFR-08 の限定的な例外(前提)として書く。
- 1件ずつの `add`・`reissue` の出力は変えない(#30 のまま。端末に1回だけ表示)。

### 3. 登録の上限を31にする

- 登録の上限を31件にする(停止中の ID も数える)。ID は `P01`〜`P31`。`P31` の次は払い出さない(32件目の登録は、`add` でも一括発行でも拒否する)。
- 31件のうち1件(`P01`)は、本番の通し確認の専用で、確認後に停止する。協力者に配るのは `P02`〜`P31` の30件。スクリプトは、確認専用かどうかを区別しない(運用の規則として README に書く)。
- 上限31は #47 で実装済み(前提を参照)。本PBIは、一括発行にも同じ上限を適用する。

### 4. 本番での発行〜ログインの通し確認(手順。コード変更なし)

- README に、実験開始の前に研究者が行う通しの確認の手順を、順番つきで書く。手順の骨子(確認専用の ID は `P01`):
  1. 台帳の登録件数を確かめる。確認専用の `P01` が台帳にすでにあれば、それを使う。台帳が空なら、確認専用の ID を1件目として `add --note` で追加する(`P01` が払い出される。備考に確認専用であることを書く。端末に表示されたパスワードを確認に使う)。台帳に `P01` 以外の件がある、または登録済みの件数と30の合計が31を超えるときは、作業を止めて PO に相談する。
  2. 協力者の30人分を一括発行し(`P02`〜`P31`)、CSV を得る。
  3. Secret Manager に設定ファイルの新しい版を追加し、Cloud Run を再デプロイする。
  4. 確認専用の ID とパスワードで、本番のログイン画面からログインし、ログイン後の画面にその ID が表示されることを確かめ、ログアウトする。
  5. 確認専用の ID を停止し、もう一度、版の追加と再デプロイを行う。確認専用の ID でログインできない(ログイン画面が失敗の文言で再表示される)ことを確かめる。
  6. CSV を使って協力者に配布し、配布が済んだら CSV を削除する。
- 失敗したときに見る点(起動の失敗のログに出る環境変数の名前、シークレットの読み取り権限、マウント先のパス)を書く。
- 確認専用の ID でログインすると、その ID の視聴ログなどが本番の DB に残りうる。分析のときに、その ID(`P01`)の記録を除くことを README に書く。
- 今回の実験(2026-10-27 開始)の31件は、#47 の作業で手動で発行済み(POの意図)。今回の実験の台帳には、一括発行で追加できる枠が残っていない。この手順を今回の実験で実施したか(AC16 の扱い)は「未解決の論点」Q10。
- README の「(未確認)」の3項目(`--set-secrets` のファイルマウントの書式、マウント先の制約、シークレットの大きさの上限)は、Cloud Run と Secret Manager の公式ドキュメントで確かめ、確かめた項目は出典(URL と確認日)を添えて「(未確認)」を外す。確かめられなかった項目は「(未確認)」と理由を残す。PO の本番確認(AC16)の後、マウントの書式の項目に「本番で動作を確認(日付)」を書き足す。

## 受入基準
